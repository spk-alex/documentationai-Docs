# Matter Cluster 29 — Descriptor Cluster

<Callout type="info">
Matter Cluster <code>29</code>, also written as <code>0x001D</code>, is the <strong>Descriptor Cluster</strong>.
The Descriptor cluster is meant to replace the support from the Zigbee Device Object (ZDO) for describing a node, its endpoints and clusters. This cluster describes an endpoint instance on the node, independently from other endpoints, but also allows composition of endpoints to conform to complex device type patterns. This cluster supports a list of one or more device type identifiers that represent conformance to device type specifications.
</Callout>

## Cluster 29 Features

The `FeatureMap` attribute (`1/29/65532`) is a bitmap. Each bit set means the device implements that feature and the attributes and commands that depend on it.

| Bit | Code | Feature | Conformance | Meaning |
|---:|---|---|---|---|
| 0 | `TAGLIST` | TagList | `desc` | The TagList attribute is present |

Example: `FeatureMap` = `0` means no optional feature is enabled; `1` means every feature listed above is enabled.

# Attribute Details

## Attribute `0` / `0x0000` — `DeviceTypeList`

Path example:

```text
1/29/0
```

This is a list of device types and corresponding revisions declaring endpoint conformance. At least one device type entry is present. An endpoint must conform to all device types listed in the DeviceTypeList. A cluster instance that is in common for more than one device type in the DeviceTypeList is supported as a shared cluster instance on the endpoint.

| Property | Value |
|---|---|
| Type | list of DeviceTypeStruct |
| Conformance | `M` |
| Access | R (read: view) |
| Constraint | min 1 entries |
| Default | `desc` |

Each entry is a `DeviceTypeStruct` (see Data Types).

Example:

```json
{
  "1/29/0": []
}
```

## Attribute `4` / `0x0004` — `TagList`

Path example:

```text
1/29/4
```

This attribute is used to disambiguate sibling endpoints in certain situations, as defined in the Disambiguation section in the System Model specification. An example of such a situation might be a device with two buttons, with this attribute being used to indicate which of the two endpoints corresponds to the button on the left side.

| Property | Value |
|---|---|
| Type | list of SemanticTagStruct |
| Conformance | `TAGLIST` |
| Access | R (read: view) |
| Constraint | 1 to 6 entries |
| Default | `MS` |

Example:

```json
{
  "1/29/4": []
}
```

# Cluster 29 Commands

Cluster 29 defines **no commands**. It is read (and, for writable attributes, written) through attribute access only.

# Cluster 29 Events

Cluster 29 defines **no events**.

# SmartphoneKey Notes

- Descriptor is read on every endpoint at commissioning to detect device types and bridge structure (`PartsList`). The primary device type is selected from `DeviceTypeList` for the shadow.
- Shadow paths follow `endpoint/29/attribute`; attribute values that the device reports as unreadable are written as `n/a`.
- Attribute IDs, command IDs and enum values on this page come from the CSA Matter 1.6.1 data model; descriptions are condensed from the specification text.
