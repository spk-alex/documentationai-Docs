# Matter Cluster 53 — Thread Network Diagnostics

<Callout type="info">
Matter Cluster <code>53</code>, also written as <code>0x0035</code>, is the <strong>Thread Network Diagnostics Cluster</strong>.
It is served by every Matter node that has a Thread radio and reports how that node is attached to the Thread mesh: its role, channel, PAN, neighbors, routes, and radio counters. It is a diagnostics cluster: it does not control the device and it does not configure the Thread network.
</Callout>

## Cluster Identity

| Field | Value |
|---|---|
| Cluster ID decimal | `53` |
| Cluster ID hex | `0x0035` |
| Cluster name | `Thread Network Diagnostics` |
| Cluster revision (Matter 1.6.1) | `3` |
| Typical endpoint | `0` (root endpoint, one instance per node) |
| Spec section | Core Specification, "Thread Network Diagnostics Cluster" |

Thread Network Diagnostics is a **node-level** cluster. It lives on endpoint `0` next to Basic Information (40), General Diagnostics (51), and Network Commissioning (49). A node has exactly one Thread radio, so there is never more than one instance.

Related clusters:

| Cluster | Role |
|---|---|
| 49 Network Commissioning | Adds the Thread operational dataset to the node during commissioning (`AddOrUpdateThreadNetwork`). |
| 51 General Diagnostics | Lists the Thread interface in `NetworkInterfaces` with its IPv6 addresses and `InterfaceType` = Thread. |
| 1106 Thread Border Router Management | Served by a **border router** (hub), exposes the active/pending dataset it is running. |
| 1107 Thread Network Directory | Served by a hub, lists the Thread networks it knows about. |

## Shadow Path Format

Attribute paths follow the usual format:

```text
endpoint / 53 / attribute
```

Example:

```text
0/53/1
```

| Part | Meaning |
|---|---|
| `0` | Root endpoint |
| `53` | Thread Network Diagnostics cluster |
| `1` | `RoutingRole` attribute |

<Callout type="warning">
<strong>SmartphoneKey bridge behaviour.</strong> The Matter bridge deliberately excludes cluster <code>53</code> from the device <em>state</em> shadow (together with cluster <code>62</code> Operational Credentials), because the neighbor and route tables plus 60+ counters add roughly 3&nbsp;KB per device and change constantly. As a result <code>0/53/*</code> paths are <strong>not present in device shadows</strong> even though the bridge reads them from the node. Thread topology for a hub is available through the hub-side OTBR tooling (<code>ot-ctl</code>, the thread-topology viewer) and through the bridge logs, not through the shadow.
</Callout>

## Features (`FeatureMap`, attribute `65532`)

The feature map tells you which optional counter groups the node implements.

| Bit | Code | Feature | Attributes it unlocks |
|---:|---|---|---|
| 0 | `PKTCNT` | PacketCounts | Rx/Tx packet counts (`22`–`55`, packet-oriented subset) |
| 1 | `ERRCNT` | ErrorCounts | `OverrunCount` (`6`) and the error counters |
| 2 | `MLECNT` | MLECounts | Mesh Link Establishment role/attach counters `14`–`21` |
| 3 | `MACCNT` | MACCounts | MAC layer Tx/Rx counters `22`–`55` |

A `FeatureMap` of `0` is valid: the node then serves only the mandatory topology attributes (`0`–`13`, `59`–`64`). Battery-powered sleepy end devices commonly report `0` or only `MLECNT`.

## Attributes

All attributes are read-only. "Nullable" means the node returns `null` when it is not attached to a Thread network (role `Unassigned`/`Unspecified`). Conformance is from the 1.6.1 data model: **M** mandatory, **O** optional, or the feature that makes it mandatory.

### Network identity and topology (`0`–`13`)

| ID | Attribute | Type | Conf. | Nullable | Meaning |
|---:|---|---|---|---|---|
| 0 | `Channel` | uint16 | M | yes | IEEE 802.15.4 channel in use (`11`–`26` for 2.4 GHz). |
| 1 | `RoutingRole` | `RoutingRoleEnum` | M | yes | Current MLE role of the node. See the enum below. |
| 2 | `NetworkName` | string (≤16) | M | yes | Human-readable Thread network name, for example `OpenThread-952e`. |
| 3 | `PanId` | uint16 | M | yes | 16-bit PAN ID of the Thread network. |

| 5 | `MeshLocalPrefix` | ipv6pre | M | yes | Mesh-local IPv6 prefix (`fdxx::/64`) of the network. |
| 6 | `OverrunCount` | uint64 | ERRCNT | no | Packets dropped because of buffer overrun since boot or last `ResetCounts`. |
| 7 | `NeighborTable` | list of `NeighborTableStruct` | M | no | Every neighbor the node has a direct MLE link with. Empty list when detached. |

## Data Types

### `RoutingRoleEnum` (attribute `1`)

| Value | Name | Meaning |
|---:|---|---|
| 0 | `Unspecified` | Role unknown / not reported. |
| 1 | `Unassigned` | Not attached to any Thread network (detached or disabled). |
| 2 | `SleepyEndDevice` | Sleepy end device (SED/SSED): radio off between polls. Battery sensors and locks. |
| 3 | `EndDevice` | Minimal end device with radio always on; does not route. |
| 4 | `REED` | Router-Eligible End Device: an end device that can be promoted to router. |
| 5 | `Router` | Router: forwards traffic and accepts children. Mains-powered devices. |
| 6 | `Leader` | Router that also manages router-ID assignment and Network Data. One per partition. |

For an end device the business-relevant distinction is `2`/`3` (attached) versus `1` (detached). Role changes between `4`, `5` and `6` are normal mesh self-organisation and need no action.

## Commands

| ID | Command | Direction | Conformance | Effect |
|---:|---|---|---|---|
| 0 | `ResetCounts` | client → server | mandatory if `ERRCNT` | Resets `OverrunCount` and all Tx/Rx/MLE counters to `0`. No response payload (status only). |

Use `ResetCounts` before a measurement window so counter deltas are meaningful. It does not affect topology attributes or the neighbor table.

## Interpreting the Values

### Signal quality

| Metric | Where | Good | Marginal | Bad |
|---|---|---|---|---|
| `AverageRssi` / `LastRssi` (dBm) | NeighborTable | `-25` … `-60` | `-60` … `-75` | below `-80` |
| `LQI` (0–255) | NeighborTable | above `200` | `100`–`200` | below `100` |
| `LQIIn` / `LQIOut` (0–3) | RouteTable | `3` | `2` | `0`–`1` |
| `FrameErrorRate` (%) | NeighborTable | under `5` | `5`–`20` | over `20` |

RSSI is negative dBm: closer to `0` is stronger. A sleepy end device seen at `-85 dBm` with a frame error rate above 20 % will show delayed commands, missed reports, and eventually `ParentChangeCount` climbing.

### Typical health checks

| Symptom | Attribute(s) to look at |
|---|---|
| Device "offline" but powered | `RoutingRole` = `1` Unassigned, `AttachAttemptCount` rising → cannot join; check dataset / network key (`RxErrSecCount` on neighbours). |
| Intermittent control | Parent entry in `NeighborTable` with low RSSI/LQI or high `FrameErrorRate`; `ParentChangeCount` rising. |
| Two meshes with the same name | Different `PartitionId` / `ExtendedPanId` across devices. |
| Channel interference | `TxErrCcaCount`, `TxErrBusyChannelCount`, `RxErrFcsCount` rising on the hub. |
| Leader flapping | `LeaderRouterId` changing, `LeaderRoleCount` / `PartitionIdChangeCount` rising. |

## SmartphoneKey Notes

- **Not in shadows.** `0/53/*` is filtered out of the device state shadow by the bridge (`STATE_EXCLUDED_CLUSTERS`). Do not build backend logic on these paths; they will be absent.
- **Device availability** comes from the hub's presence pipeline, not from `RoutingRole` or `ConnectionStatus`.
- **Hub-side Thread view.** On the hub the same information (and more: full topology, child tables, network data) is available through `ot-ctl` on the OTBR and the thread-topology viewer, which read the border router directly instead of polling each device over Matter.
- **Sleepy devices (locks, sensors).** Reading cluster 53 on a sleepy end device wakes it only on its next poll; expect latency of seconds to minutes and keep diagnostic reads rare. The counters on such devices are usually absent (`FeatureMap` = `0`).
- **Revision.** Devices certified against Matter 1.2–1.4 report `ClusterRevision` `1` or `2` and may lack attributes `63`/`64` (`ExtAddress`, `Rloc16`); treat missing attributes as unsupported, not as an error.
