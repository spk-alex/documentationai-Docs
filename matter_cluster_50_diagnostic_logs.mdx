# Matter Cluster 50 — Diagnostic Logs Cluster

<Callout type="info">
Matter Cluster <code>50</code>, also written as <code>0x0032</code>, is the <strong>Diagnostic Logs Cluster</strong>.
This Cluster supports an interface to a Node. It provides commands for retrieving unstructured diagnostic logs from a Node that may be used to aid in diagnostics. It will often be the case that unstructured diagnostic logs will be Node-wide and not specific to any subset of Endpoints.
</Callout>

# Cluster 50 Commands

Cluster 50 has **1 client-to-server command** and **1 response**.

| ID | Hex | Command | Direction | Conformance | Response | Description |
|---:|---|---|---|---|---|---|
| 0 | `0x00` | `RetrieveLogsRequest` | client → server | `M` | RetrieveLogsResponse | Reception of this command starts the process of retrieving diagnostic logs from a Node. |
| 1 | `0x01` | `RetrieveLogsResponse` | server → client | `M` | — | This is generated as a response to the RetrieveLogsRequest. |

## AcceptedCommandList

The `AcceptedCommandList` attribute lists the command IDs the endpoint actually implements:

```text
endpoint_id / 50 / 65529
```

```json
{
  "0/50/65529": [
    0
  ]
}
```

<Callout type="warning">
Before sending a Cluster 50 command, check that the command ID exists in <code>endpoint/50/65529</code>. Optional commands are only present when the matching feature is set in <code>FeatureMap</code>.
</Callout>

## Bridge Command Payload Format

The bridge accepts Matter commands in this structure:

```json
{
  "message_id": "1",
  "command": "device_command",
  "args": {
    "endpoint_id": 0,
    "cluster_id": 50,
    "command_name": "RetrieveLogsRequest",
    "payload": {},
    "timed_request_timeout_ms": 1000
  }
}
```

For Cluster 50, always use `"cluster_id": 50`. Payload keys are the command field names in lowerCamelCase. Octet-string fields are base64-encoded. `timed_request_timeout_ms` is required for timed commands and ignored otherwise.

# Command: `RetrieveLogsRequest`

## Purpose

Reception of this command starts the process of retrieving diagnostic logs from a Node.

## Command Identity

| Field | Value |
|---|---|
| Command ID | `0` |
| Command hex | `0x00` |
| Command name | `RetrieveLogsRequest` |
| Direction | client → server |
| Conformance | `M` |
| Response | RetrieveLogsResponse |
| Access | (invoke: operate) |

## Payload Fields

| ID | Field | Payload key | Type | Conformance | Constraint | Meaning |
|---:|---|---|---|---|---|---|
| 0 | `Intent` | `intent` | IntentEnum | `M` | — | Indicates why the diagnostic logs are being retrieved from the Node. A Node may utilize this field to selectively determine the logs to transfer. |
| 1 | `RequestedProtocol` | `requestedProtocol` | TransferProtocolEnum | `M` | — | This field is used to indicate how the log transfer is to be realized. |
| 2 | `TransferFileDesignator` | `transferFileDesignator` | string | `O` | max length 32 | This field is present if the RequestedProtocol is BDX. The TransferFileDesignator is set as the File Designator of the BDX transfer if initiated. |

`Intent` values (`IntentEnum`): `0` = EndUserSupport, `1` = NetworkDiag, `2` = CrashLogs

`RequestedProtocol` values (`TransferProtocolEnum`): `0` = ResponsePayload, `1` = BDX

## Bridge Command Example

```json
{
  "message_id": "1",
  "command": "device_command",
  "args": {
    "endpoint_id": 0,
    "cluster_id": 50,
    "command_name": "RetrieveLogsRequest",
    "payload": {
      "intent": 0,
      "requestedProtocol": 0
    }
  }
}
```

The device answers with `RetrieveLogsResponse` (see below).

# Command: `RetrieveLogsResponse`

## Purpose

This is generated as a response to the RetrieveLogsRequest. The data for this command is shown in the following.

## Command Identity

| Field | Value |
|---|---|
| Command ID | `1` |
| Command hex | `0x01` |
| Command name | `RetrieveLogsResponse` |
| Direction | server → client (response) |
| Conformance | `M` |

## Response Fields

| ID | Field | Payload key | Type | Conformance | Constraint | Meaning |
|---:|---|---|---|---|---|---|
| 0 | `Status` | `status` | StatusEnum | `M` | — | Indicates the result of an attempt to retrieve diagnostic logs. |
| 1 | `LogContent` | `logContent` | octstr | `M` | max length 1024 | This field is included in the command if the Status field has a value of Success or Exhausted. A Node should utilize this field to transfer the newest diagnostic log entries. |
| 2 | `UTCTimeStamp` | `utcTimeStamp` | epoch-us | `O` | — | — |
| 3 | `TimeSinceBoot` | `timeSinceBoot` | systemtime-us | `O` | — | This field should be included in the command if the Status field has a value of Success. |

`Status` values (`StatusEnum`): `0` = Success, `1` = Exhausted, `2` = NoLogs, `3` = Busy, `4` = Denied
