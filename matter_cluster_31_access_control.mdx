# Matter Cluster 31 — Access Control Cluster

<Callout type="info">
Matter Cluster <code>31</code>, also written as <code>0x001F</code>, is the <strong>Access Control Cluster</strong>.
The Access Control Cluster exposes a data model view of a Node's Access Control List (ACL), which codifies the rules used to manage and enforce Access Control for the Node's endpoints and their associated cluster instances. Access to this Access Control Cluster itself requires a special Administer privilege level, such that only Nodes granted such privilege (hereafter termed "Administrators") can manage the Access Control Cluster. The Access Control Cluster is present on the root node endpoint of each Node, and must NOT be present on any other Endpoint of any Node.
</Callout>

## Cluster 31 Features

The `FeatureMap` attribute (`0/31/65532`) is a bitmap. Each bit set means the device implements that feature and the attributes and commands that depend on it.

| Bit | Code | Feature | Conformance | Meaning |
|---:|---|---|---|---|
| 0 | `EXTS` | Extension | `O` | Device provides ACL Extension attribute |
| 1 | `MNGD` | ManagedDevice | `desc` | Device is managed |
| 2 | `AUX` | Auxiliary | `desc` | Some auxiliary ACL entries may be auto-generated by other features |

Example: `FeatureMap` = `0` means no optional feature is enabled; `7` means every feature listed above is enabled.

## Bridge Command Payload Format

The bridge accepts Matter commands in this structure:

```json
{
  "message_id": "1",
  "command": "device_command",
  "args": {
    "endpoint_id": 0,
    "cluster_id": 31,
    "command_name": "ReviewFabricRestrictions",
    "payload": {},
    "timed_request_timeout_ms": 1000
  }
}
```

For Cluster 31, always use `"cluster_id": 31`. Payload keys are the command field names in lowerCamelCase. Octet-string fields are base64-encoded. `timed_request_timeout_ms` is required for timed commands and ignored otherwise.

# Command: `ReviewFabricRestrictions`

## Purpose

This command signals to the service associated with the device vendor that the fabric administrator would like a review of the current restrictions on the accessing fabric. This command includes an optional list of ARL entries that the fabric administrator would like removed. In response, a ReviewFabricRestrictionsResponse is sent which contains a token that can be used to correlate a review request with a FabricRestrictionReviewUpdate event. Within 1 hour of the ReviewFabricRestrictionsResponse, the FabricRestrictionReviewUpdate event is generated, in order to indicate completion of the review and any additional steps required by the user for the review.

The server must generate AccessControlEntryChanged events whenever its ACL attribute data is changed by an Administrator. - Each added entry must generate an event with ChangeType Added. - Each changed entry must generate an event with ChangeType Changed. - Each removed entry must generate an event with ChangeType Removed.

## Event `2` — `FabricRestrictionReviewUpdate`

The server must generate a FabricRestrictionReviewUpdate event to indicate completion of a fabric restriction review. Due to the requirement to generate this event within a bound time frame of successful receipt of the ReviewFabricRestrictions command, this event may include additional steps that the client may present to the user in order to help the user locate the user interface for the Managed Device feature.

| ID | Field | Type | Conformance | Meaning |

## Event `3` — `AuxiliaryAccessUpdated`

The server must generate AuxiliaryAccessUpdated events whenever its AuxiliaryACL attribute data changes due to system management operations. This event should be generated only once per batch of changes, if many changes are done together. Administrators may use this event to trigger re-evaluation of overall access control currently granted to the node.
